# 案例归因与体系审查

## 从现象建立证据链

收集用户请求、上下文与数据版本、执行 Trace、工具参数和响应、最终产物、评分版本及判定证据。Trace 指可取得的执行记录，不承诺访问模型未公开的内部思维。

先核对任务和标准是否合理，再寻找执行中首次可证实的偏差。结果不对并不直接证明模型能力不足。

| 竞争假设 | 需要的证据或区分方法 |
|---|---|
| 判定标准或评分器有误 | 人工核对规则，检查单位、容差、等价输出和证据缺失 |
| 环境与依赖异常 | 同版本在可比环境复现，核对工具状态和数据快照 |
| 意图或范围理解错误 | 对照用户要求与实际使用的时间、对象和范围 |
| 规划或工具参数错误 | 找到首次错误参数或遗漏步骤，验证其对结果的影响 |
| 上下文或数据丢失 | 核对当次可见输入、截断和检索结果 |
| 计算、状态更新或交付错误 | 对照中间产物、实际状态与最终输出 |
| 模型能力限制 | 排除可证实的环境和实现问题，以重复且可比的任务支持判断 |

将每条结论标成已确认、支持但未证实、待排除。相关性不直接等于根因；对真实数据做修改或重放有副作用的任务前，应先使用合适的隔离环境。

## 案例记录的最小字段

记录 case_id、来源、任务与版本、观察结果、预期依据、证据位置、判定状态、竞争假设、根因置信程度、下一步、负责人或责任角色。

同时检查两条改进路径：

1. Agent 修改：针对有证据的偏差修改代码、Prompt、工具、上下文或数据处理。
2. 评测修改：补样本、澄清规则、修复评分器，或修正与真实使用不符的分布。

修复关联复现任务及相邻合法反例。例如重复记录去重的修复，还要确认不同 ID 的同额记录未被误删。仅有修复建议时不能把状态写为已解决。

案例来源影响代表性。用户投诉、异常筛选、规则采样与随机抽样需保留来源字段；不能用高风险筛选集的失败率估计全部线上失败率。

## 成熟度审查

基于目标项目的证据填写，而不是要求每个项目同时建设完整平台：

| 能力 | 可核验的证据 |
|---|---|
| 观测 | 某个真实任务能追溯到输入、工具、产物与版本 |
| 任务资产 | 有可复现的任务、规则、数据与维护方式 |
| 判定可信度 | 有正确和错误结果校验、人机分歧复核 |
| 回测 | 新旧版本可比较，门禁和错误处理明确 |
| 线上观察 | 指标有分母、覆盖范围、影响控制和解释方式 |
| 案例归因 | 现象可追到证据，并有未确认假设的区分办法 |
| 改进回流 | 至少一条案例能追到修改、回归任务和复核结果 |

对每项标注存在、部分存在、缺失或未知，附文件或记录引用。没有查到资料应写未知，不直接评为缺失。若项目使用 L0—L3 等级，先读取其实际定义，不自造等级后冒充原文标准。

排序时结合用户影响、问题发生范围、证据强度、修复依赖与成本。选择能打通当前反馈流程的下一步，而不是给所有团队推荐同一套平台。
