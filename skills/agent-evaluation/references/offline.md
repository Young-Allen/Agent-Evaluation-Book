# 离线评测设计与版本比较

## 从任务定义到评分

选取目标业务中的实际任务。读取现有样本格式；没有格式时，适配 [任务模板](../assets/task.yaml)。不要为了使用此模板要求项目迁移框架。

Task 应明确：任务标识、用户输入、前置上下文、环境与权限、参考结果或允许行为、最终产物或状态、检查规则。动态时间、工具数据、历史记忆和残留文件会影响执行时，应固定或记录其版本。

对长程任务，检查实际 outcome：文件是否存在且内容正确、数据库是否达到目标状态、用户目标是否完成。最终回复中的自述不能代替产物证据。

过程检查用于定位与必要约束。若 SQL、脚本或不同工具顺序都能正确完成任务，不把其中一种路径写成硬性通过条件。只在权限、交易顺序等业务规则确有要求时强制顺序。

## 样本覆盖与用途

使用一个轻量矩阵标记任务类型、数据形态、边界条件和重要性。至少考虑目标行为应发生与不应发生两面，但不强行规定样本数量。

端到端与过程是范围维度；黄金、历史错题、挑战与必过是用途或发布策略维度，不能混为互斥分类。一个任务可以拥有多个标签。

调参样本与最终验证样本应区分。用同一批任务反复修改 Prompt 后得到的分数主要说明对已见样本的适配程度，不能直接推广到全部流量。采样分布和覆盖缺口随报告提供。

## 评分逻辑

| 判断对象 | 适合的方法 | 实现注意点 |
|---|---|---|
| 数值、文件、结构、最终状态 | 程序检查 | 明确单位、容差、缺失与重复的口径 |
| 证据支持、内容完整、交互质量 | 细粒度 Rubric，人工或模型判定 | 输出判断依据；证据不足允许 unknown |
| 关键行为约束 | 工具事件与状态检查 | 单次调用成功不代表业务成功 |

判定逻辑本身也需要正例和反例。至少验证：已知正确结果可通过，目标错误可被抓到，等价合法结果不被误伤，缺证据不会通过。增加项目内评分器时，围绕这些性质做必要验证，不测试文档措辞。

评分器不得把任务输出、网页、日志中携带的指令当成自己的评价指令。模型判定需要固定规则和可追踪版本，并抽样核对人机分歧；不能把另一个模型的结论直接当作不可争议事实。

## 有效版本对比

记录 task_id、trial_id、agent_version、dataset_version、rubric_version、grader_version、environment_id。基线与候选运行相同的任务分布。支持时优先逐任务比较，便于识别改善和退化位置。

区分以下状态：

- pass：必要检查通过。
- fail：有充分证据表明任务或规则失败。
- unknown：证据不足，无法可靠判定。
- error：执行或评分基础设施故障；进一步注明是预期故障场景还是评测平台故障。

如果工具故障恢复能力本身是任务目标，则该工具故障属于被测场景，不能统一排除为基础设施错误。

结果同时列出发起总次数、各状态数和重试次数。若统计 pass / (pass + fail)，同时披露 unknown 与 error 的占比及排除原因，避免通过排除失败运行抬高分数。任务平均与 Trial 平均需标明权重。

## 随机性与指标术语

Pass Rate 是在约定分母上的观测通过比例；pass@k 衡量 k 次中至少一次成功；pass^k 衡量 k 次全部成功。三者不是同义词。

在每次独立且成功概率恒为 p 的简化模型下，至少一次成功为 1-(1-p)^k，全部成功为 p^k。真实运行存在共享服务故障或状态污染时，不能直接假定独立性。不要用增加重试后的 pass@k 冒充单次可靠性改善。

报告重复次数、预算、失败波动和不确定性。数据规模足够且决策确有需要时再计算合适的区间；不设置脱离任务的固定显著性或成功率阈值。

## 发布条件与结果解释

硬性条件、一般质量和资源预算分开报告。阈值取自业务要求或项目配置，缺失时写待定与建议依据；示例数值必须标成示例。

离线通过支持“已覆盖任务上未发现阻断项”，不能证明没有未覆盖风险。离线失败也要先查评分和环境，不能默认归罪于模型。

需要接入 CI 时沿用项目现有流程：运行 → 评分 → 保留结果与失败证据 → 根据明确门禁决定状态。基础设施 error 不应自动放行。不要因为制定评测方案就顺带修改生产发布流程。
